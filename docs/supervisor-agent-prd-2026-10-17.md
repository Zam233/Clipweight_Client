## 1. 背景：为什么现在必须做

上一轮走读已确认三个事实（均可在代码中定位）：

1. **质检是盲的。** `QualityInput` 只有 `timeline / constraints / creative_brief / production_plan` 四个字段，没有任何「上游发生了什么」的信息。
2. **归因是一张静态表。** `agents/quality_agent.py:348-357` 把「错误类别 → 重做哪个 Agent」写成 if/elif，不是诊断。
3. **自愈没有记忆。** `_quality_issues` / `_quality_heal_count` 只注入被重做的 Agent，不注入质检；第二轮质检不知道自己试过谁、试过几次。结果是同一症状 → 同一 `redo_agent` → 重复三次 → 管线失败，用户看到的只有 `pipeline_v2.py:1082` 那句「质检未通过（自愈重试用尽），请查看质检问题后重试或调整输入」。
4. **失败原因只有一句话，甚至没有。** 6 个输出类（`schema/agent.py`）各自重复定义 `error: Optional[str]`——失败原因是一个自由字符串；而大量降级（LLM 超时走 fallback、素材源无结果用占位）是 `decision=PASS` + `error=None`，连这句话都不落。所以即便秘书想归因，也拿不到可用输入。详见 F9。

同时，**这些信息在系统里本来就存在**：`trace` 里记着 `agent_start / agent_end / error / warning`，`AgentBus` 也在 `publish`，但 `AgentBus.get_events()` 全仓零消费者。所以真正的缺口不是「没有记录」，而是**记录没有被任何决策方读取**。

本需求要解决的，就是把这个缺口补上，并把「谁来决定重做谁、用什么策略、用哪个模型」这件事交还给一个可审计的决策者。

## 2. 目标与非目标

### 2.1 目标（可衡量）

| 编号 | 目标 | 现状 | 目标值 |
|---|---|---|---|
| G1 | 失败可解释率（失败管线中能给出「责任阶段＋证据＋建议」的比例） | ≈0%（只有一句通用错误） | ≥90% |
| G2 | 无效重复重做（同一策略连续重试次数） | 最多 3 次同策略 | ≤1 次后必须换策略或上报 |
| G3 | 单成片 LLM 成本的可控性 | 无预算概念，失败重试不设上限 | 每管线硬上限，超限前必须叫停 |
| G4 | 秘书带来的成本增量（成功路径） | — | **0**（默认不唤起） |
| G5 | 秘书决策时延对总时长的影响 | — | ≤5% |

### 2.2 非目标（本期明确不做，见 §3 红线）

- ❌ 不改变六阶段主干的执行顺序（顺序由数据依赖唯一确定）
- ❌ 不让秘书写 timeline、不碰渲染、不直接调用 44 个工具
- ❌ 不让秘书的账本信息进入质检的评分路径（保留盲审）
- ❌ 不做多智能体自由协商（agent 之间不互相对话）
- ❌ 不在本期做「用户口述一句话 → 自动产出多集」这类自动选题编排

## 3. 角色与边界（红线）

| 角色 | 做 | 不做（产品级红线，需在接口权限层兜底，不能只靠提示词） |
|---|---|---|
| **调度中枢 Supervisor（秘书）** | 读账本、裁定归因、选策略、下派工单（含指定模型）、写诊断书、叫停超预算 | 不写 timeline；不调渲染/素材下载/44 个工具；不改变阶段顺序；不代替质检打分；不静默花超预算的钱 |
| **阶段 Agent（structure/material/edit/animation/audio）** | 按派工单执行，产出/修改 timeline | 不自选模型（模型由派工单指定）；不越权重做别的阶段 |
| **质检 Quality** | 只判成品好坏，输出 issues（盲审） | 不接收账本；不决定重做策略（裁定权归秘书） |
| **用户** | 看诊断书、一键执行建议、接管派工 | — |

> **红线一的表述**：账本 → 归因 → 派工，这条路可以走 LLM；账本 → 质检评分，这条路**必须断开**。质检一旦知道「上游超时了」，就会自我合理化放过缺陷，整套自愈退化为自动签批通过。

## 4. 触发模型：默认零开销

秘书不是常驻轮询，是**事件唤起**。这是成本红线（G4）的实现方式。

| 触发事件 | 是否唤起 | 秘书期望动作 |
|---|---|---|
| 阶段 Agent 返回 FAIL / 抛异常 | ✅ | 裁定归因（是不是上游造的因） |
| 质检检出 error 且 self-heal 第 1 轮 | ✅ | 裁定归因 + 选策略 + 派工 |
| 质检第 2 轮仍同一症状 | ✅ | **强制换策略**（禁止再走同参数重做） |
| 账本出现「降级」标记且影响成品合格性 | ✅ | 判定：接受降级并告知用户 / 换源重做 / 上报 |
| 预算达 70% | ✅ | 降级策略（切更便宜模型、放弃非关键阶段） |
| 预算达 100% | ✅ | 立即止损，出诊断书，转人工 |
| 用户中途改指令（改片/改需求） | ✅ | 重新规划受影响阶段 |
| 正常成功路径 | ❌ | 零 LLM 调用，行为与现状完全一致 |

**验收**：关闭秘书开关时，管线行为、耗时、成本必须与现状 bit-level 等价（同一份 timeline 产出）。

## 5. 功能需求

### F1 账本读取与摘要

**用户故事**：作为决策方，我需要在不读日志的情况下知道这条管线每一步发生了什么，以便判断问题出在哪一步。

- **行为**：秘书获取一份结构化摘要（不是原始日志流），包含每个阶段的：尝试序号、输入摘要、决策、**降级列表**、警告、错误、耗时、用量、所用模型。
- **降级（degradation）定义**：任何「为了不中断而退而求其次」的行为都必须打标并登记，至少覆盖：LLM 超时走 fallback 场景、素材源无结果用占位、RAG 检索失败、TTS 回退默认音色、类型插件 transform 失败保留原时间线。
- **输入**：pipeline_id
- **输出**：账本摘要（≤4000 字，可裁剪）
- **边界**：秘书只读，不写账本。
- **验收**：任取一条历史失败管线，摘要中能定位到「哪个阶段降级／失败、影响哪个场景」。

### F2 归因裁定

**用户故事**：作为用户，我要知道到底是谁搞坏的，而不是笼统告诉我去重试。

- **行为**：输入「质检症状 + 账本证据」→ 输出责任阶段、证据引用（账本条目 id）、置信度（高/中/低）、是否**不可修复**。
- **关键规则**：
  - 上游有降级/失败证据且症状可解释时，**责任归上游**，不得归症状所在阶段（例如：structure 未给 `material_refs` → material 空 → edit 产出 0 长度片段，症状在 edit，责任在 structure）。
  - 判定为「资源缺失」（如素材源两次无结果）时，标记不可修复，**不得**进入无意义重试。
- **输出**：归因结论（一个主责任阶段 + 可选上游连带阶段）
- **验收**：抽样 30 条失败管线人工核对，责任阶段判对 ≥80%；「不可修复」判定不得把可修复的缺陷误标（误标率 ≤10%，因为误标会直接放弃可救的片子）。

### F3 策略选择

**用户故事**：同一招用两次不管用，就换招。

- **行为**：从策略库中选一个，并在派工单中写明理由。
- **策略库（本期固定 6 种，不开放自由生成）**：

| 编号 | 策略 | 适用 | 影响 |
|---|---|---|---|
| S1 | 同参重做 | 首次尝试、疑似偶发 | 最低成本 |
| S2 | 换模型重做 | 同阶段同模型已失败 | 中成本，见 F8 |
| S3 | 上游联动重做 | 归因指向更上游阶段 | 中高成本 |
| S4 | 降级接受并标注 | 不可修复但可交付 | 零成本，必须告知用户 |
| S5 | 换实现路径 | 同阶段两次无效（换素材源/换分镜策略/缩短段落） | 高成本 |
| S6 | 止损上报 | 预算/轮次耗尽、或缺陷不可接受 | 终止管线 |
- **硬规则**：同一策略对同一阶段**不得连续使用超过 1 次**（G2）。
- **验收**：构造「重做 edit 三次无效」的用例，秘书必须在第 2 轮改走 S3/S5，而不是重复 S1。

### F4 派工单（DispatchOrder）

**用户故事**：作为阶段 Agent，我收到的必须是明确的活儿，不是一句「重做」。

- **字段（业务语义）**：任务目标阶段、要修的具体问题（引用质检 issue）、期望验收条件（改完必须满足什么）、上游已尝试历史（禁止重复路径）、预算与超时、**指定模型**（F8）、是否允许降级。
- **行为**：秘书下单 → 编排层按单执行确定性阶段 → 结果回账本 → 秘书复核。
- **边界**：派工单不能要求阶段做它不负责的事（例如让 audio 改分镜）。
- **验收**：每张派工单可完整回答「派给谁、修什么、用什么模型、花多少钱、什么算修好」，缺一即为不合格派工单。

### F5 诊断书

**用户故事**：我要看懂为什么失败、下一步做什么，而不是读工程师日志。

- **内容（固定结构）**：一句话结论 / 问题与影响（第几段、多严重）/ 证据链（最多 3 条，人话）/ 已尝试（做了什么、为什么没用）/ 建议动作（1-3 条，可一键执行）/ 成本与耗时。
- **语言**：面向创作者，不使用 `agent`、`stage`、`token` 等内部术语（对外用「选材」「剪辑」「配音」「质检」）。
- **反例（现状）**：「质检未通过（自愈重试用尽），请查看质检问题后重试或调整输入。」
- **正例**：「第 3 段没找到可用的素材镜头，已用占位图顶上；重做选材和剪辑各一次都没解决。建议：允许这一段无素材，或把这句文案缩短到 4 秒。—— 你选哪个？」
- **验收**：5 名非技术用户可用性测试，≥4 人能复述「为什么失败 ＋ 下一步做什么」。

### F6 预算与止损

- **行为**：管线级硬预算（金额，可按套餐下发）；达 70% 提示秘书走降级策略、切便宜模型；达 100% 立即止损，不再重试，落诊断书。
- **边界**：秘书无权提额；提额只能由用户/管理员操作。
- **验收**：模拟「重试导致成本飙升」场景，管线不得越过硬上限；超限前必须有 ≥1 次降级尝试或明确的止损决策。

### F7 升级与人工接管

- **行为**：三种情况必须转人工并保留现场：①连续两轮换策略仍不过；②判定不可修复且用户未授权降级；③预算耗尽。
- **人工接管**：用户可在「调度面板」查看历史派工单、手动改派工单（改目标阶段/模型/策略）、或直接接受当前成片。
- **验收**：接管后管线可继续执行，且改派记录进入账本（谁改的、改了什么）。

### F8 子代理模型路由（本需求的核心新能力）

**用户故事**：作为决策方，我知道哪个阶段值得花大模型的力气、哪个阶段用便宜的够用，并且能在失败时换一个模型再试一次。

> 详细规格见 §6。

### F9 失败回报契约（向上传递）

**用户故事**：作为调度中枢，我不该靠猜上游为什么失败——失败的那一方必须把原因、证据和它需要什么一并交上来。

这是 F1 账本的**入口约定**：账本里 80% 的内容由这一层上报，而不是编排层代填。

- **行为**：每个阶段 Agent 每次 `execute()` 返回时，必须同时交回一个结构化失败/降级回报（而非一句 `error` 字符串）。
- **失败回报字段（业务语义）**：

| 字段 | 含义 | 为什么必须有 |
|---|---|---|
| 归因类别 | 资源缺失 / 输入不足 / 模型能力不足 / 超时 / 外部服务不可用 / 约束冲突 / 自身缺陷 | 决定策略是「重试」「换模型」还是「必须找上游」 |
| 阻塞点 | 哪个场景、第几段、哪条轨道（人话 + 结构定位） | 决定重做的**粒度**——不必整段重来 |
| 已尝试 | 做了几次、每次改了什么 | 防止秘书重复已失败的路径 |
| 可重试性 | 同参重试有意义 / 需上游补齐 / 需人工 / 永久不可修复 | 直接映射到 F3 策略库 |
| **请求上游提供什么** | `[{上游阶段, 需补的字段, 为什么}]` | **本次需求最大的收益点**：归因从「推断」变成「申报」 |
| 证据引用 | 素材 id / LLM 响应 id / 时间线位置 | 诊断书里的人话证据链 |
| 降级声明 | 降级了什么、降成什么、影响范围 | 让秘书判断「能否接受降级并交付」 |

- **硬规则（四条）**：
  1. **降级也必须上报。** `decision=PASS` 不等于没问题——用了占位图、回退了默认音色、保留了原时间线，都必须登记。否则秘书看到的是「一切正常」，而成片里有占位图。
  2. **禁止静默吞错。** `except: pass`、`llm_or_fallback` 直接返回 fallback 而不留原因，一律视为缺陷。降级可以发生，但必须留痕。
  3. **必须能「向上要东西」。** 允许下游直接申报「我需要 structure 补 scene 3 的 material_refs」，而不是自己硬撑出残片。
  4. **失败回报不进质检评分路径**（红线延续，见 §3）。
- **边界**：Agent 只申报事实与需求，不决定重做谁——裁定权仍在秘书（F2）。
- **验收**：
  - 全部 6 个 Agent 的 FAIL 分支必须填充完整失败回报；降级路径必须填充降级声明。用 Pydantic validator + 契约测试双卡，新增 Agent 忘填则测试直接红。
  - 任取一条历史失败管线，能答出「哪一段、什么类别、试过几次、需要谁补什么」。

> **为什么归 F9 在 P0**：账本是壳，失败回报是内容。只建壳不建约定，账本就会退化成「编排队代填的日志」，秘书一样盲。

## 6. F8 专项：子代理模型选择

### 6.1 用户可感知的能力

- 秘书派工时，可以为**每次**阶段执行指定 provider / model。
- 换模型是有依据的、可解释的：「选材用便宜模型两次没找到合适镜头，第三次换强模型」。
- 用户能在成本条上看懂：这次换了模型，贵了多少。

### 6.2 路由决策依据（按优先级）

| 优先级 | 信号 | 说明 |
|---|---|---|
| 1 | 预算余量 | 余量不足 → 只允许降价，不允许升价 |
| 2 | 该阶段同模型的失败历史 | 同模型已失败 → 优先换模型（F3-S2）而非重试 |
| 3 | 任务类型 | 判定/校验类（结构校验、字幕对齐）走便宜轨；创作类（分镜、动画编排、文案）走强轨 |
| 4 | 时延窗口 | 剩余时间紧 → 选快模型 |
| 5 | 用户/套餐策略 | 免费套餐只能用便宜轨；付费可开强轨 |

### 6.3 治理红线

1. **白名单**：只能从配置的模型白名单里选，不得任意拼 provider/URL。
2. **不得自我提权**：秘书不能因为「觉得难」就无限升级到最贵模型；升级必须受 §6.2 优先级 1、5 约束。
3. **留痕**：每次选择必须记入账本：目标阶段、选定模型、理由、上一次同任务所用模型、预估成本。
4. **不可自选的位置**：渲染、发布、计费等安全敏感路径**不得**由秘书指定模型。
5. **失败计费归因**：模型 A 失败不得污染模型 B 的熔断计数（技术约束见 §6.5）。
6. **降级链**：指定模型不可用时，按预设回退链降级并记账，不得静默换成默认模型而不告知。

### 6.4 冷启动策略（避免第一天就让模型乱花钱）

| 阶段 | 行为 | 门限 |
|---|---|---|
| 一阶段（上线首月） | 秘书只能从**静态路由表**里选（每个阶预先配 2-3 个候选：便宜/标准/强） | 默认行为 |
| 二阶段 | 开放「表内自由选」，但仍受白名单与预算约束 | 累计 ≥50 条带模型标注的账本 |
| 三阶段 | 开放策略性换模型（含跨 provider） | 阶段二的一次成功率提升 ≥5% 且成本不升 |

### 6.5 技术约束（设计必须遵守，产品验收需覆盖）

| 约束 | 现状 | 影响 |
|---|---|---|
| 模型选择目前是二元的 `use_flash: bool` | `services/llm.py:410,476`；`settings.llm_flash_model` 可单独启用 | 需升级为 `model_spec(provider, model, params)`；客户端可按 provider 复用，model 逐次透传 |
| 熔断按键 = agent 名 | `pipeline_v2.py:470-539` 类级 `_circuit_breakers: dict[str, dict]` | 引入模型后必须扩为 `(stage, model)`，否则 A 模型失败会连坐 B 模型 |
| 子代理通道只接受插件 Agent | `services/_subagent_body.txt` 走 `AgentRegistry.get()`；`agents/registry.py:52` 明确禁止注册核心 6 名 | 秘书要派的**恰恰是核心阶段**，因此派工应复用编排层 `_dispatch`，而非现有 subagent 通道 |
| 子代理深度上限 2 | `_SUBAGENT_MAX_DEPTH = 2`（宿主 0 → 子 1，子不能再派生） | 秘书属于编排层，不透支该深度预算，需显式厘清 |
| 用量记账已有复合名机制 | `_attributed_name = "{host}:{sub}"` → `llm_tracker.record_llm_call(model=...)` | 模型选择天然可归因、可观测，无需新建计量体系 |
| 前端已有模型清单接口 | `api/providers.py`（`POST /api/providers/{id}/models` 覆盖模型清单）＋ `settings_runtime` 可运行时改 | 路由表配置界面可复用，不必新建模型管理模块 |

## 7. 用户界面需求

### 7.1 管线详情页 · 调度面板

- 时间线式决策记录：一步一行「读到了什么 → 判定 → 派给谁 → 用什么模型 → 花了多少 → 结果」。
- 折叠默认，只展示决策点（不含常规成功阶段）。
- 每行可展开原始证据（账本条目引用）。

### 7.2 诊断书卡片

- 出现时机：管线失败 / 判定不可修复 / 停损。
- 结构见 F5；动作按钮至少 3 个：`按建议重试`、`换策略`、`接受当前成片`。
- 一键动作必须二次确认（说明预计成本与耗时）。

### 7.3 成本条

- 常驻显示「已花 / 预算」，模型切换时显示增量预估。
- 达 70% 变黄、100% 变红并冻结重试。

### 7.4 实时性

- 复用现有 **SSE-only** 实时链路（`/api/pipeline/trace/stream/{pipeline_id}`），不新增 WebSocket。

## 8. 数据对象（业务语义）

| 对象 | 一句话 | 关键字段（业务含义） |
|---|---|---|
| 失败回报 `FailureReport` | 一个阶段失败或降级时，向上交回的原因单（F9） | 归因类别、阻塞点、已尝试、可重试性、请求上游提供的字段、证据引用、降级声明 |
| 账本条目 `LedgerEntry` | 一个阶段一次尝试的完整记录 | 阶段、第几次尝试、输入摘要、决策、降级列表、警告、错误、耗时、用量、所用模型、时间戳（其中失败/降级部分来自 `FailureReport`） |
| 归因结论 `Attribution` | 这次失败怪谁 | 主责任阶段、连带上游、证据引用（账本条目）、置信度、是否不可修复 |
| 派工单 `DispatchOrder` | 一张要执行的工单 | 目标阶段、要修的 issue、验收条件、禁用路径（已试过的）、模型、预算、超时、是否允许降级 |
| 诊断书 `DiagnosisReport` | 给人看的一页结论 | 结论、问题与影响、证据链、已尝试、建议动作（可执行）、成本与耗时 |

## 9. 非功能需求

| 类别 | 要求 |
|---|---|
| 可观测 | 每次秘书决策必须可在调度面板回放：输入摘要、判定、模型、成本、结果 |
| 成本 | 成功路径零增量；失败路径单次决策 ≤ 阈值（见 §12 待定）；硬预算不可越 |
| 时延 | 单次决策 ≤ 8s（不含实际修复耗时）；等待期间 UI 必须有进度，不得白屏 |
| 幂等 | 同一账本状态下重复决策应产生同一致结论（可复现，便于排障） |
| 安全 | 秘书无文件/渲染/网络写权限；模型选择受白名单约束 |
| 回滚 | 提供开关：关闭秘书后完全退回现状行为（含关闭模型路由） |
| 上报完整性 | 阶段结束时「有降级但无登记」必须能被检出：账本条目数 ≠ 降级计数即为异常，记入管线诊断 |
| 数据合规 | 跨 provider 调用需在套餐/隐私条款中披露（见 §12） |

## 10. 验收标准

| 编号 | 标准 | 验证方式 |
|---|---|---|
| A1 | 失败管线 ≥90% 产出诊断书且含「责任＋证据＋建议」 | 抽样 30 条历史失败管线回放 |
| A2 | 归因准确率 ≥80% | 人工核对 30 条 |
| A3 | 同策略连续重试 ≤1 次 | 构造「重做三次无效」用例 |
| A4 | 不可修复判定误标率 ≤10% | 人工核对 |
| A5 | 成功路径成本增量 = 0 | A/B 各 20 条同输入管线对比 token 账单 |
| A6 | 不越过硬预算 | 模拟成本飙升场景 |
| A7 | 质检评分路径未收到账本字段 | 契约测试（断言 `QualityInput` 不含账本字段） |
| A8 | 诊断书可被非技术用户读懂 | 5 人可用性测试，≥4 人通过 |
| A9 | 模型路由留痕完整 | 任取一条换模型记录，五个字段齐全 |
| A10 | 关闭开关后行为与现状等价 | 同输入产出 timeline 逐字节比对 |
| A11 | 6 个 Agent 的 FAIL 分支全部填充完整失败回报（七字段无缺） | 契约测试 ＋ 逐阶段构造失败用例回放 |
| A12 | 所有降级路径均产生降级声明，无静默吞错 | 静态扫描「`except: pass` / fallback 无记录」清单，逐项确认归零 |
| A13 | 下游「向上申报需求」能触发正确的上游重做 | 构造「material 申报缺 material_refs」用例，验证秘书走 S3 而非重做 material 自身三次 |

## 11. 分期与依赖

| 期 | 范围 | 交付物 | 依赖 |
|---|---|---|---|
| **P0**（先做） | F9 失败回报契约（结构化失败/降级上报）＋ F1 账本（落库降级、警告、错误、模型、用量） | 账本能回答「这一步到底发生了什么、它自己说了什么」 | 无 |
| **P1** | F2 归因（确定性优先，仅冲突时用 LLM）＋ F5 诊断书 v1（模板化，无 LLM） | 失败可解释率从 0 到 ≥70% | P0 |
| **P2** | F3 策略 + F4 派工 + F8 模型路由（表内选） | 无效重试下降、成本可控 | P0、P1 |
| **P3** | F6 预算止损 + F7 升级接管 + 调度面板完整交互 | 可交付运营 | P2 |
| **P4**（可延后） | F8 二/三阶段（自由选、跨 provider） | 成本结构优化 | P2 跑满一个月数据 |

> **顺序不可颠倒的理由**：没有 P0 的账本，秘书和今天的质检一样盲；先上秘书只会多一层 LLM 费用和一个新的不确定性来源。P1 落地后会发现一部分「需要判断」的场景自动消失（信息一全，静态归因就够准），剩下的才是秘书真正该干的活。

## 12. 待裁定问题（需拍板）

| 编号 | 问题 | 影响 |
|---|---|---|
| Q1 | 每管线硬预算金额与计费口径（按 token 折算还是按次） | F6 无法开工 |
| Q2 | 免费套餐是否开放秘书与模型路由 | 直接影响成本模型与 G4 |
| Q3 | 是否允许用户手动改派工单（人工接管深度） | F7 范围大小 |
| Q4 | 单次秘书决策成本上限、单管线最大换模型次数 | F3/F8 硬规则 |
| Q5 | 是否允许跨 provider 选模型（数据出境/合规） | F8 三阶段能否开启 |
| Q6 | 诊断书是否允许暴露内部阶段名（专业用户可能需要） | F5 文案与权限 |

### 12.1 推荐默认值（待签字，签字后即为「已定」）

> 这些值的作用是让 B3/B4/B5 能开工。它们不是拍脑袋的大数，而是**从机制反推出来的最小值**：先定「怎么算」，再定「具体数字」。

| 编号 | 推荐值 | 依据 | 需要你确认的点 |
|---|---|---|---|
| **Q1-a 计费口径** | 按 **token 折算货币**（复用 `llm_tracker` 的 model + input/output tokens × 路由表单价），不按次、不按分钟 | 现成数据已经在记，按次会掩盖长 prompt 的差异；按分钟与 LLM 成本无关 | 单价表由谁维护（配置里写死 / 后台可改） |
| **Q1-b 硬预算** | 分级：`预算 = 该管线预估成本 × 2.5`，且夹在 **[下限, 上限]** 区间内；预估取自 structure 产出后的 token 估算 | 2.5 倍足以覆盖「一次失败 + 一次重做」；低于此值重试必被腰斩 | 区间上下限的具体金额（需你按定价表填） |
| **Q2 免费套餐** | 账本 + 诊断书**可见**；秘书**只跑 shadow 不派工**；模型路由锁 `cheap` 档 | 让免费用户体验「说得清为什么失败」，但不承担自动重试的失败成本 | 是否允许免费用户手动点「按建议重试」（会产生一次额外成本） |
| **Q4-a 换模型次数** | 每管线 **≤2 次** | 超过 2 次说明不是模型能力问题，而是输入/资源问题，继续换是烧钱 | 是否按套餐分档（付费可放宽到 4 次） |
| **Q4-b 单次决策成本** | 秘书单次决策 ≤ **该阶段单次执行均值 × 0.15**；绝对上限按定价表填 | 决策本身不该比执行还贵 | 绝对上限数值 |
| **Q4-c 决策模型档位** | 归因/策略决策固定走 `cheap` 档（`use_flash`） | 这是分类与选择任务，不需要最强模型 | 是否允许「归因冲突」时升一档 |
| **Q5 跨 provider** | 默认**不跨**，只允许同一 provider 内换档 | 数据出境/合规风险可控，且换 provider 会让记账与回归口径漂移 | 是否对「本地 ollama」例外（无出境问题） |

## 13. 风险与缓解

| 风险 | 后果 | 缓解 |
|---|---|---|
| 归因错误被放大 | 秘书自信地重做错阶段，比现状更贵更慢 | 置信度低时降级为「静态归因 + 上报」，不硬派工；A2 门限卡住上线 |
| 「换模型」变成「花钱试错」 | 成本飙涨 | 白名单 + 预算硬熔断 + 冷启动只允许表内选 |
| 用户信任 | 自动重试静默发生，用户不知道钱花在哪 | 调度面板 + 成本条 + 一键动作二次确认 |
| 引入 LLM 决策后不可复现 | 排障困难 | 决策幂等（同账本同结论）＋ 关开关可退现状 |
| 账本信息回流质检 | 自愈退化为自动签批 | A7 契约测试硬卡 |

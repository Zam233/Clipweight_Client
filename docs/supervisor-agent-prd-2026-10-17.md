## 1. 背景：为什么现在必须做

上一轮走读已确认三个事实（均可在代码中定位）：

1. **质检是盲的。** `QualityInput` 只有 `timeline / constraints / creative_brief / production_plan` 四个字段，没有任何「上游发生了什么」的信息。
2. **归因是一张静态表。** `agents/quality_agent.py:348-357` 把「错误类别 → 重做哪个 Agent」写成 if/elif，不是诊断。
3. **自愈没有记忆。** `_quality_issues` / `_quality_heal_count` 只注入被重做的 Agent，不注入质检；第二轮质检不知道自己试过谁、试过几次。结果是同一症状 → 同一 `redo_agent` → 重复三次 → 管线失败，用户看到的只有 `pipeline_v2.py:1082` 那句「质检未通过（自愈重试用尽），请查看质检问题后重试或调整输入」。
4. **失败原因只有一句话，甚至没有。** 6 个输出类（`schema/agent.py`）各自重复定义 `error: Optional[str]`——失败原因是一个自由字符串；而大量降级（LLM 超时走 fallback、素材源无结果用占位）是 `decision=PASS` + `error=None`，连这句话都不落。所以即便秘书想归因，也拿不到可用输入。详见 F9。

同时，**这些信息在系统里本来就存在**：`trace` 里记着 `agent_start / agent_end / error / warning`，`AgentBus` 也在 `publish`，但 `AgentBus.get_events()` 全仓零消费者。所以真正的缺口不是「没有记录」，而是**记录没有被任何决策方读取**。

本需求要解决的，就是把这个缺口补上，并把「谁来决定重做谁、用什么策略、用哪个模型」这件事交还给一个可审计的决策者。

## 2. 目标与非目标

### 2.1 目标（可衡量）

| 编号 | 目标 | 现状 | 目标值 |
|---|---|---|---|
| G1 | 失败可解释率（失败管线中能给出「责任阶段＋证据＋建议」的比例） | ≈0%（只有一句通用错误） | ≥90% |
| G2 | 无效重复重做（同一策略连续重试次数） | 最多 3 次同策略 | ≤1 次后必须换策略或上报 |
| G3 | 单成片 LLM 成本的可控性 | 无预算概念，失败重试不设上限 | 预算可配置：配置时超限前必须叫停；未配置时如实记账、不阻断 |
| G4 | 秘书带来的成本增量（成功路径） | — | **0**（默认不唤起） |
| G5 | 秘书决策时延对总时长的影响 | — | ≤5% |
| G6 | 并行子代理状态可见率（运行中的子代理能被用户看到） | 0%（无此概念） | 100% |
| G7 | 命令/脚本执行的可审计率 | — | 100%（含被拒绝的） |

### 2.2 非目标（本期明确不做，见 §3 红线）

- ❌ 不改变六阶段主干的执行顺序（顺序由数据依赖唯一确定）
- ❌ 秘书不直接写 timeline 字段——它通过**派生/派工子代理**去改，保证每次改片都有产物与责任人
- ❌ 不让秘书的账本信息进入质检的评分路径（保留盲审）
- ❌ 不做「子代理之间互相协商」的网状通信：所有子代理只与秘书单线交互（星型，不是网型）
- ❌ 不在运行时把 LLM 生成的 Python 注册成长期插件或常驻 Agent（临时脚本可以，长期身份必须走已注册的 worker 蓝图）
- ❌ 不在本期做「用户口述一句话 → 自动产出多集」这类自动选题编排

## 3. 角色与边界（红线）

| 角色 | 做 | 不做（产品级红线，需在接口权限层兜底，不能只靠提示词） |
|---|---|---|
| **调度中枢 Supervisor（秘书）** | 读账本、裁定归因、选策略、下派工单（可指定任意 provider/model）、**派生新子代理**、查看/列出/取消子代理、执行 pwsh/bash 与 python（用于诊断与验证）、写诊断书、叫停超预算 | 不直接写 timeline 字段（只能通过子代理改）；不改六阶段顺序；不代替质检打分；不静默花超预算的钱；**不得裸执行命令**（必须经 ExecutionGateway：沙盒 + 审计 + 限额）；不得在运行时把 LLM 生成的代码注册成长期插件；不得读凭据/密钥文件 |
| **子代理（阶段 Agent / 动态 Worker）** | 按派工单或派生规格执行，产出/修改 timeline，或完成指派的诊断/验证任务 | 不自选模型（模型由派工单/派生规格指定）；不越权重做别的阶段；不派生自己的子代理（星型拓扑，只有秘书能派生） |
| **质检 Quality** | 只判成品好坏，输出 issues（盲审） | 不接收账本；不决定重做策略（裁定权归秘书） |
| **用户** | 看诊断书、一键执行建议、接管派工、审批高风险命令 | — |

> **红线一（信息）**：账本 → 归因 → 派工，这条路可以走 LLM；账本 → 质检评分，这条路**必须断开**。质检一旦知道「上游超时了」，就会自我合理化放过缺陷，整套自愈退化为自动签批通过。
>
> **红线二（执行）**：秘书拥有 shell / python 权限**不代表它可以为所欲为**——所有执行必须经过统一的执行网关（§F11），网关承担五件事：**独立风险判定**、沙盒隔离、超时与资源上限、全量审计、硬底线的额外一道确认。绕过网关直接 `subprocess` 视为实现缺陷，由测试卡死。
>
> **红线三（身份）**：秘书可以**在运行时派生新的子代理**，但派生对象只能是两种之一：①已注册 worker 蓝图的实例化；②由「角色名 + 提示词 + 工具allowlist + 模型 + 预算」组成的**临时 worker 规格**。它不能凭空生成代码并把代码注册为常驻 Agent——那条路会让系统在无人 review 的情况下自我扩权。
>
> **红线四（拓扑）**：子代理与秘书是**星型**关系（只与秘书单线通信），不允许子代之间横向对话。横向对话会让归因链断裂，且成本不可预算。

## 4. 触发模型：默认零开销

秘书不是常驻轮询，是**事件唤起**。这是成本红线（G4）的实现方式。

| 触发事件 | 是否唤起 | 秘书期望动作 |
|---|---|---|
| 阶段 Agent 返回 FAIL / 抛异常 | ✅ | 裁定归因（是不是上游造的因） |
| 质检检出 error 且 self-heal 第 1 轮 | ✅ | 裁定归因 + 选策略 + 派工 |
| 质检第 2 轮仍同一症状 | ✅ | **强制换策略**（禁止再走同参数重做） |
| 账本出现「降级」标记且影响成品合格性 | ✅ | 判定：接受降级并告知用户 / 换源重做 / 上报 |
| 预算达 70% | ✅ | 降级策略（切更便宜模型、放弃非关键阶段） |
| 预算达 100% | ✅ | 立即止损，出诊断书，转人工 |
| 用户中途改指令（改片/改需求） | ✅ | 重新规划受影响阶段 |
| 用户下达诊断/运维指令（「查一下这段为什么没声音」） | ✅ | 读账本 → 必要时执行只读命令/脚本验证 → 回答 |
| 子代理主动上报 `needs_upstream` | ✅ | 归因 + 决定是否重派上游 |
| 正常成功路径 | ❌ | 零 LLM 调用，行为与现状完全一致 |

**验收**：关闭秘书开关时，管线行为、耗时、成本必须与现状 bit-level 等价（同一份 timeline 产出）。

## 5. 功能需求

### F1 账本读取与摘要

**用户故事**：作为决策方，我需要在不读日志的情况下知道这条管线每一步发生了什么，以便判断问题出在哪一步。

- **行为**：秘书获取一份结构化摘要（不是原始日志流），包含每个阶段的：尝试序号、输入摘要、决策、**降级列表**、警告、错误、耗时、用量、所用模型。
- **降级（degradation）定义**：任何「为了不中断而退而求其次」的行为都必须打标并登记，至少覆盖：LLM 超时走 fallback 场景、素材源无结果用占位、RAG 检索失败、TTS 回退默认音色、类型插件 transform 失败保留原时间线。
- **输入**：pipeline_id
- **输出**：账本摘要（≤4000 字，可裁剪）
- **边界**：秘书只读，不写账本。
- **验收**：任取一条历史失败管线，摘要中能定位到「哪个阶段降级／失败、影响哪个场景」。

### F2 归因裁定

**用户故事**：作为用户，我要知道到底是谁搞坏的，而不是笼统告诉我去重试。

- **行为**：输入「质检症状 + 账本证据」→ 输出责任阶段、证据引用（账本条目 id）、置信度（高/中/低）、是否**不可修复**。
- **关键规则**：
  - 上游有降级/失败证据且症状可解释时，**责任归上游**，不得归症状所在阶段（例如：structure 未给 `material_refs` → material 空 → edit 产出 0 长度片段，症状在 edit，责任在 structure）。
  - 判定为「资源缺失」（如素材源两次无结果）时，标记不可修复，**不得**进入无意义重试。
- **输出**：归因结论（一个主责任阶段 + 可选上游连带阶段）
- **验收**：抽样 30 条失败管线人工核对，责任阶段判对 ≥80%；「不可修复」判定不得把可修复的缺陷误标（误标率 ≤10%，因为误标会直接放弃可救的片子）。

### F3 策略选择

**用户故事**：同一招用两次不管用，就换招。

- **行为**：从策略库中选一个，并在派工单中写明理由。
- **策略库（本期固定 6 种，不开放自由生成）**：

| 编号 | 策略 | 适用 | 影响 |
|---|---|---|---|
| S1 | 同参重做 | 首次尝试、疑似偶发 | 最低成本 |
| S2 | 换模型重做 | 同阶段同模型已失败 | 中成本，见 F8 |
| S3 | 上游联动重做 | 归因指向更上游阶段 | 中高成本 |
| S4 | 降级接受并标注 | 不可修复但可交付 | 零成本，必须告知用户 |
| S5 | 换实现路径 | 同阶段两次无效（换素材源/换分镜策略/缩短段落） | 高成本 |
| S6 | 止损上报 | 预算/轮次耗尽、或缺陷不可接受 | 终止管线 |
- **硬规则**：同一策略对同一阶段**不得连续使用超过 1 次**（G2）。
- **验收**：构造「重做 edit 三次无效」的用例，秘书必须在第 2 轮改走 S3/S5，而不是重复 S1。

### F4 派工单（DispatchOrder）

**用户故事**：作为阶段 Agent，我收到的必须是明确的活儿，不是一句「重做」。

- **字段（业务语义）**：任务目标阶段、要修的具体问题（引用质检 issue）、期望验收条件（改完必须满足什么）、上游已尝试历史（禁止重复路径）、预算与超时、**指定模型**（F8）、是否允许降级。
- **行为**：秘书下单 → 编排层按单执行确定性阶段 → 结果回账本 → 秘书复核。
- **边界**：派工单不能要求阶段做它不负责的事（例如让 audio 改分镜）。
- **验收**：每张派工单可完整回答「派给谁、修什么、用什么模型、花多少钱、什么算修好」，缺一即为不合格派工单。

### F5 诊断书

**用户故事**：我要看懂为什么失败、下一步做什么，而不是读工程师日志。

- **内容（固定结构）**：一句话结论 / 问题与影响（第几段、多严重）/ 证据链（最多 3 条，人话）/ 已尝试（做了什么、为什么没用）/ 建议动作（1-3 条，可一键执行）/ 成本与耗时。
- **语言**：面向创作者，不使用 `agent`、`stage`、`token` 等内部术语（对外用「选材」「剪辑」「配音」「质检」）。
- **反例（现状）**：「质检未通过（自愈重试用尽），请查看质检问题后重试或调整输入。」
- **正例**：「第 3 段没找到可用的素材镜头，已用占位图顶上；重做选材和剪辑各一次都没解决。建议：允许这一段无素材，或把这句文案缩短到 4 秒。—— 你选哪个？」
- **验收**：5 名非技术用户可用性测试，≥4 人能复述「为什么失败 ＋ 下一步做什么」。

### F6 预算与止损（可配置，默认不启用）

- **行为**：管线级硬预算是**可选配置项**（在设置中填金额与单价表）。配置后：达 70% 提示秘书走降级策略、切便宜模型；达 100% 立即止损、不再重试、落诊断书。
- **未配置时（默认）**：预算视为**无上限**，不阻断、不降级；成本条仍显示已花金额（只观测，不设闸）。这是有意识的取舍——用「花多少算多少」换「不被截断的排查能力」。
- **边界**：秘书无权提额；提额只能是用户/管理员在设置里改配置。
- **验收**：分两段——已配置时不得越过硬上限；未配置时不得出现任何「因预算被拒」的派工（如实记录花费即可）。

### F7 升级与人工接管

- **行为**：三种情况必须转人工并保留现场：①连续两轮换策略仍不过；②判定不可修复且用户未授权降级；③预算耗尽。
- **人工接管**：用户可在「调度面板」查看历史派工单、手动改派工单（改目标阶段/模型/策略）、或直接接受当前成片。
- **验收**：接管后管线可继续执行，且改派记录进入账本（谁改的、改了什么）。

### F8 子代理模型路由（本需求的核心新能力）

**用户故事**：作为决策方，我知道哪个阶段值得花大模型的力气、哪个阶段用便宜的够用，并且能在失败时换一个模型再试一次。

> 详细规格见 §6。

### F9 失败回报契约（向上传递）

**用户故事**：作为调度中枢，我不该靠猜上游为什么失败——失败的那一方必须把原因、证据和它需要什么一并交上来。

这是 F1 账本的**入口约定**：账本里 80% 的内容由这一层上报，而不是编排层代填。

- **行为**：每个阶段 Agent 每次 `execute()` 返回时，必须同时交回一个结构化失败/降级回报（而非一句 `error` 字符串）。
- **失败回报字段（业务语义）**：

| 字段 | 含义 | 为什么必须有 |
|---|---|---|
| 归因类别 | 资源缺失 / 输入不足 / 模型能力不足 / 超时 / 外部服务不可用 / 约束冲突 / 自身缺陷 | 决定策略是「重试」「换模型」还是「必须找上游」 |
| 阻塞点 | 哪个场景、第几段、哪条轨道（人话 + 结构定位） | 决定重做的**粒度**——不必整段重来 |
| 已尝试 | 做了几次、每次改了什么 | 防止秘书重复已失败的路径 |
| 可重试性 | 同参重试有意义 / 需上游补齐 / 需人工 / 永久不可修复 | 直接映射到 F3 策略库 |
| **请求上游提供什么** | `[{上游阶段, 需补的字段, 为什么}]` | **本次需求最大的收益点**：归因从「推断」变成「申报」 |
| 证据引用 | 素材 id / LLM 响应 id / 时间线位置 | 诊断书里的人话证据链 |
| 降级声明 | 降级了什么、降成什么、影响范围 | 让秘书判断「能否接受降级并交付」 |

- **硬规则（四条）**：
  1. **降级也必须上报。** `decision=PASS` 不等于没问题——用了占位图、回退了默认音色、保留了原时间线，都必须登记。否则秘书看到的是「一切正常」，而成片里有占位图。
  2. **禁止静默吞错。** `except: pass`、`llm_or_fallback` 直接返回 fallback 而不留原因，一律视为缺陷。降级可以发生，但必须留痕。
  3. **必须能「向上要东西」。** 允许下游直接申报「我需要 structure 补 scene 3 的 material_refs」，而不是自己硬撑出残片。
  4. **失败回报不进质检评分路径**（红线延续，见 §3）。
- **边界**：Agent 只申报事实与需求，不决定重做谁——裁定权仍在秘书（F2）。
- **验收**：
  - 全部 6 个 Agent 的 FAIL 分支必须填充完整失败回报；降级路径必须填充降级声明。用 Pydantic validator + 契约测试双卡，新增 Agent 忘填则测试直接红。
  - 任取一条历史失败管线，能答出「哪一段、什么类别、试过几次、需要谁补什么」。

> **为什么归 F9 在 P0**：账本是壳，失败回报是内容。只建壳不建约定，账本就会退化成「编排队代填的日志」，秘书一样盲。

### F10 动态子代理（派生与复用）

**用户故事**：作为决策方，现有 6 个阶段覆盖不了所有情况——我需要临时派一个新角色（例如「素材可用性核查员」「字幕校对员」）去干活，而不是把活硬塞给某个阶段。

- **两条派生路径**：
  1. **复用已注册 worker**：核心 6 阶段 + 插件注册的 agent（后者需先解除「核心名不可派生」的限制，见 §6.5）。
  2. **按规格现场派生临时 worker**：`{role_name, system_prompt, tool_allowlist, model_spec, timeout_sec, budget_usd, max_turns}`。临时 worker **只服务本次管线**，管线结束即回收，不写入 `AgentRegistry`、不成为常驻能力。
- **边界（硬）**：
  - 子代理**不得再派生子代理**（星型拓扑，深度固定 1 层）。
  - 临时 worker 的工具集只能是主代理工具集的**子集**——不能借子代理绕过执行网关。
  - **并发上限**由设置项 `max_concurrent_subagents` 控制（默认 6，用户可在设置中改）。
  - **子代理开销不设独立上限**：全额计入管线总预算（若管线硬预算未启用，则子代理开销同样不限）。这是一条有意识的取舍——用「看得见的成本」换「不被截断的排查能力」，所以 F6 的成本条必须把子代理开销单列出来。
  - 临时 worker 的 system_prompt 若由 LLM 生成，必须落库留档并在控制台可见（事后可追责）。

**执行权限的审核门（带 shell/python 的 worker 必过）**：

1. **独立 LLM 风险判定**：由**独立会话 + 独立模型**只读 `WorkerSpec`（角色名、system_prompt、工具集、预算、轮次），输出 `{risk: low|med|high, reasons[], 建议}`。与 F11 的命令风险判定**复用同一个 `risk_judge`**（同一套输入隔离约束，避免两处标准漂移）。
   - **独立性是硬要求**：不接收主代理的任何解释与上下文，否则「我要做运维诊断」这句话就能把它说服。
2. **人工审核**：审核人在控制台看到风险等级、理由、完整 system_prompt 与工具集，批准或拒绝；`risk=high` 时必须显式二次确认，不得一键通过。
3. **未过门不得实例化**：两级结论（LLM 风险等级 + 人工决定）连同审核人、时间一并入账本。
4. **无执行权限的 worker**（只读分析/文案类）不必过门，仅落库 + 控制台可见即可。
- **验收**：能派一个「素材可用性核查员」检查第 3 段是否为占位图，结论写回账本；管线结束后该 worker 从可用列表消失。

**自动派生（v1.5 用户决策：允许）**：`supervisor_mode=on` 且归因置信度为 `low` 时，编排层**自动**派一个
「失败现场核查员」去看现场，结论写回 trace（含花费与耗时）。四条边界：
① 只授只读工具（`read_file` / `list_dir` / `list_subagents`），因此**不需要**执行权限审核门；
② `shadow` / `off` 模式一律不派生（保证关闭开关后的等价性）；③ 同一阶段只派一次；
④ 派出去是后台任务，核查员跑多久都不耽误自愈决策。设置项 `supervisor_auto_spawn` 可关。

### F11 执行能力（ExecutionGateway）

**用户故事**：作为诊断方，我需要真的去看文件、跑 ffprobe、跑一段脚本验证假设，而不是只会「再试一次」。

**能力清单（固定五项）**：

| 编号 | 能力 | 说明 |
|---|---|---|
| E1 | `spawn_subagent` | 发起子代理（F10），返回 subagent_id |
| E2 | `get_subagent_status` | 查单个子代理的状态与输出摘要 |
| E3 | `list_subagents` | 列出本管线所有子代理（树形/扁平） |
| E4 | `run_shell` | 执行 pwsh（Windows）/ bash（POSIX）命令 |
| E5 | `run_python` | 执行 Python 脚本（子进程） |

**统一网关行为（红线二的落地）**：

| 维度 | 规定 |
|---|---|
| 风险判定（独立 LLM 请求） | agent 每次要执行命令，先发一个**独立的判定请求**：独立会话/独立模型，输入只含「命令原文 + cwd + workspace 说明」，**不含主 agent 的对话与其辩解**。输出 `{risk_level: low\|med\|high\|critical, reasons[], danger_explanation}` |
| 分流 | `low` → 直接执行并记账；`med` / `high` → **弹框请用户授权**，弹框必须写清「危险等级 + 会动到什么 + 可能的后果」；`critical`（含命中硬底线）→ 授权窗口点过之后**再弹一道「再次确认」窗口**，两道都过才执行 |
| 就高不就低 | 确定性规则表只做**升级**不做降级：命中危险种子（删/移/覆盖既有文件、装包、起服务、改权限、网络下载后执行）时，即便 LLM 判 `low` 也强制升为 `med` 弹框 |
| 判定失败 | 超时/解析失败/输出不合 schema → fail-safe 为 `high`（弹框），**不得**静默放行 |
| 判定开销与时延 | 判定模型由**独立配置项** `risk_judge_model` 指定（与主代理模型解耦，未配置时用 `cheap` 档）；**该模型必须命中 provider 白名单**（共用主代理的模型白名单，不另开通道）；单次判定超时默认 **5s**（可配），超时按 fail-safe 处理；串行命令逐条判定，不批处理 |
| 硬底线（**v1.5 起改为 LLM 判定 + 两级确认**） | 仅两类，由确定性规则**标记**：① 读取凭据（`.env` / `~/.ssh` / keychain）；② 不可逆系统破坏（格式化系统盘、`shutdown`/`reboot`、删除系统级注册表项）。命中后**仍交独立 LLM 判定**（让判定器给出它自己的理由），但等级被钉在 `critical`（只升不降），并要求**两级人工确认**：授权窗口 + 再次确认窗口。设置项 `exec_hard_floor_never_authorizable=true` 可回退为「规则直接拒绝、任何模式不可授权」 |
| 自动模式（用户开关） | 前端提供自动模式开关，由用户决定；开启后**只减免 `med` 的弹框**，`high` / `critical` 仍弹；开关状态入账、可随时关闭；**默认关** |
| 沙盒 | cwd 固定为管线 workspace；墙钟默认 60s（可配至 600s）；CPU/内存上限；输出截断（保留 head/tail）；**环境变量白名单，剥离全部 API Key/Token** |
| 审计 | 每条执行入账本：发起方、完整命令、cwd、**风险等级**、**独立判定的理由与危险说明**、退出码、耗时、输出摘要、是否被拒及原因、当时是否开启自动模式；不可关闭 |
| Python 约定 | 必须在**子进程**执行（禁止 in-process `exec`）；脚本先落临时文件再运行；默认禁网（可配置开启用于诊断） |

> **「独立判定」的三条可检验约束**（否则「独立」只是说法）：
> ① **输入隔离**：判定请求体只含命令与 cwd，**断言不含**主代理的对话、理由、账本上下文（A24）；
> ② **独立模型/会话**：不复用主代理的会话与实例，避免同一上下文自我背书；
> ③ **只就高不就低**：确定性规则可升级风险等级，永不允许下调（A25）；判定失败一律升到 `high`（A26）。
>
> 这三条是在你的「由独立 LLM 判定」之上加的护栏——不是不相信判定，而是不让「被说服」直接变成「被授权」。

> **诚实声明**：以上是**审计与误操作边界**，不是强安全边界。若未来要跑不可信代码，必须换成容器/VM 级隔离——本 PRD 不承诺进程级沙盒能防住恶意逃逸。

- **验收**：跑 `ffprobe` 查出某段无声并把结论写进诊断书；构造 `rm -rf /` 被拒且账本留痕；构造读取 `.env` 被拒；每条命令都能在控制台回放。

### F12 子代理观测（控制台）

**用户故事**：秘书能派生多个子代理，我必须能看见它们在干什么、花了多少、卡在哪。

- **列表与状态**：树形（秘书 → 子代理），每节点显示：角色名、状态（pending/running/done/failed/cancelled）、耗时、所用模型、累计成本、最后一条输出摘要。
- **实时性**：SSE 推送 `subagent_start / subagent_progress / subagent_end`，复用现有 SSE-only 链路。
- **可干预**：用户可取消单个子代理；取消后其产出丢弃并记账（与管线取消同语义）。
- **验收**：一条管线同时跑 3 个子代理，控制台显示 3 个节点且状态实时变化；取消其中 1 个后状态变 cancelled、并发额度立即释放。

## 6. F8 专项：子代理模型选择

### 6.1 用户可感知的能力

- 秘书派工时，可以为**每次**阶段执行指定 provider / model。
- 换模型是有依据的、可解释的：「选材用便宜模型两次没找到合适镜头，第三次换强模型」。
- 用户能在成本条上看懂：这次换了模型，贵了多少。

### 6.2 路由决策依据（按优先级）

| 优先级 | 信号 | 说明 |
|---|---|---|
| 1 | 预算余量 | 余量不足 → 只允许降价，不允许升价 |
| 2 | 该阶段同模型的失败历史 | 同模型已失败 → 优先换模型（F3-S2）而非重试 |
| 3 | 任务类型 | 判定/校验类（结构校验、字幕对齐）走便宜轨；创作类（分镜、动画编排、文案）走强轨 |
| 4 | 时延窗口 | 剩余时间紧 → 选快模型 |
| 5 | 部署形态 | 本地/私有部署优先选本地或同区 provider；云端部署可跨区（跨 provider 已开放，见 §6.3） |

### 6.3 治理红线

1. **白名单**：只能从配置的模型白名单里选（白名单项 = `provider + model` 组合），不得任意拼 URL 或未登记模型。
2. **不得自我提权**：秘书不能因为「觉得难」就无限升级到最贵模型；升级必须受 §6.2 优先级 1、5 约束。
3. **留痕**：每次选择必须记入账本：目标阶段、选定模型（含 provider）、理由、上一次同任务所用模型、预估成本。
4. **不可自选的位置**：渲染、发布、计费等安全敏感路径**不得**由秘书指定模型。
5. **失败计费归因**：模型 A 失败不得污染模型 B 的熔断计数（技术约束见 §6.5）。
6. **降级链**：指定模型不可用时，按预设回退链降级并记账，不得静默换成默认模型而不告知。
7. **跨 provider 已开放，记账不阻断**：每次跨 provider 调用都要记录「数据从哪家发往哪家」，但这只是**观测**，不是拦路——记账不得成为跨 provider 的否决权。私有化部署默认优先本地 provider（不强制）。
8. **子代理不得放宽约束**：派给子代理的模型必须在主代理允许集内；子代理没有「再选一个更贵的」权限。

### 6.4 冷启动策略（避免第一天就让模型乱花钱）

| 阶段 | 行为 | 门限 |
|---|---|---|
| 一阶段（上线首月） | 秘书主要从**静态路由表**里选（每阶段预配 2-3 个候选：便宜/标准/强），跨 provider 需命中白名单显式项 | 默认行为 |
| 二阶段 | 开放「表内自由选」（含跨 provider），受预算与白名单约束 | 累计 ≥50 条带模型标注的账本 |
| 三阶段 | 允许秘书为新派生的临时 worker 自主确定模型档位 | 一阶段一次成功率提升 ≥5% 且成本不升 |

> 跨 provider **不再是「三阶段才开放」的能力**，而是从一阶段起就在白名单内可用；三阶段开放的是「临时 worker 的档位自主决定」。

### 6.5 技术约束（设计必须遵守，产品验收需覆盖）

| 约束 | 现状 | 影响 |
|---|---|---|
| 模型选择目前是二元的 `use_flash: bool` | `services/llm.py:410,476`；`settings.llm_flash_model` 可单独启用 | 需升级为 `model_spec(provider, model, params)`；客户端可按 provider 复用，model 逐次透传 |
| 熔断按键 = agent 名 | `pipeline_v2.py:470-539` 类级 `_circuit_breakers: dict[str, dict]` | 引入模型后必须扩为 `(stage, model)`，否则 A 模型失败会连坐 B 模型 |
| 核心 6 阶段不可作为子代理 | `agents/registry.py:19-21,52` 用 `CORE_AGENT_NAMES` 禁止注册；`_subagent_body.txt` 只走 `AgentRegistry.get()` | F10 必须新增**编排层派工通道**，而不是解除 registry 黑名单——解黑名单会污染插件语义（插件 Agent 与核心阶段的生命周期/校验不同） |
| 子代理深度上限 2 且语义为「宿主→子」 | `_SUBAGENT_MAX_DEPTH = 2`（宿主 0 → 子 1，子不能再派生） | 与 F10 的星型拓扑天然一致；秘书属编排层，**不透支**该深度预算，需显式文档化 |
| 无执行网关 | 现有 44 个 tool 走 `ToolRegistry`；无命令分级、无沙盒、无审计 | F11 必须新建 `ExecutionGateway`。**不得**把 shell 当普通 tool 塞进 `ToolRegistry`——会被 `StructureAgent` 的 `with_tools`（`list_agent_callable`）一并暴露给阶段 Agent |
| 无「临时 worker」概念 | `AgentRegistry` 是插件注册表，没有运行时规格/句柄 | F10 需独立 `WorkerRegistry`（内存规格 + 任务句柄），生命周期跟管线走，不写入 `AgentRegistry` |
| 用量记账已有复合名机制 | `_attributed_name = "{host}:{sub}"` → `llm_tracker.record_llm_call(model=...)` | 模型选择与多子代理天然可归因、可观测，无需新建计量体系 |
| 前端已有模型清单接口 | `api/providers.py`（`POST /api/providers/{id}/models` 覆盖模型清单）＋ `settings_runtime` 可运行时改 | 路由表配置界面可复用，不必新建模型管理模块 |

## 7. 用户界面需求

### 7.1 管线详情页 · 调度面板

- 时间线式决策记录：一步一行「读到了什么 → 判定 → 派给谁 → 用什么模型 → 花了多少 → 结果」。
- 折叠默认，只展示决策点（不含常规成功阶段）。
- 每行可展开原始证据（账本条目引用）。

### 7.2 诊断书卡片

- 出现时机：管线失败 / 判定不可修复 / 停损。
- 结构见 F5；动作按钮至少 3 个：`按建议重试`、`换策略`、`接受当前成片`。
- 一键动作必须二次确认（说明预计成本与耗时）。

### 7.3 成本条

- 常驻显示花费；**配置了预算时**显示「已花 / 预算」并给出模型切换的增量预估；**未配置预算时只显示已花金额**，不显示进度比例、不冻结任何操作。
- 配置了预算时：达 70% 变黄、100% 变红并冻结重试。
- 子代理开销**单列一行**（F10 不设独立上限，但必须可见）。

### 7.4 实时性

- 复用现有 **SSE-only** 实时链路（`/api/pipeline/trace/stream/{pipeline_id}`），不新增 WebSocket。

### 7.5 子代理控制台（F12）

- 树形展示「秘书 → 子代理」：角色名、状态、模型、耗时、成本、最后一条输出。
- 状态色与管线一致（pending/running/done/failed/cancelled）；不可用颜色单编码，配图标与文字。
- 每节点提供「取消」；取消需二次确认并提示「该子代理已产生的成本不退还」。

### 7.6 执行日志（F11）

- 每条命令一行：`时间 · 风险等级徽标 · 命令（截断）· 退出码 · 耗时`，点开看完整输出与 cwd。
- 被拒绝的命令用独立样式并显示拒绝原因（例如「硬底线：读凭据」）。
- **自动模式开关**放在此处（执行日志头部）：一个明确的开关按钮 + 当前状态文案（「自动模式：关 — 危险命令将逐条请你确认」/「自动模式：开 — 中危命令将直接执行，高危仍会询问」）；切换即时生效并写入账本。
- 每条执行都显示独立 LLM 给出的**风险等级与理由**，便于用户事后抽查判定质量。
- **授权弹框必须说明危险程度**：等级（低/中/高/极高）+ 具体会动到什么（哪个目录/哪些文件）+ 可能的后果 + 建议动作。禁止只显示一句「是否允许执行」。
- 提供「复制命令」与「在本地重放」提示（便于用户自己复现问题）。

## 8. 数据对象（业务语义）

| 对象 | 一句话 | 关键字段（业务含义） |
|---|---|---|
| 失败回报 `FailureReport` | 一个阶段失败或降级时，向上交回的原因单（F9） | 归因类别、阻塞点、已尝试、可重试性、请求上游提供的字段、证据引用、降级声明 |
| 账本条目 `LedgerEntry` | 一个阶段一次尝试的完整记录 | 阶段、第几次尝试、输入摘要、决策、降级列表、警告、错误、耗时、用量、所用模型、时间戳（其中失败/降级部分来自 `FailureReport`） |
| 归因结论 `Attribution` | 这次失败怪谁 | 主责任阶段、连带上游、证据引用（账本条目）、置信度、是否不可修复 |
| 派工单 `DispatchOrder` | 一张要执行的工单 | 目标阶段、要修的 issue、验收条件、禁用路径（已试过的）、模型、预算、超时、是否允许降级 |
| 诊断书 `DiagnosisReport` | 给人看的一页结论 | 结论、问题与影响、证据链、已尝试、建议动作（可执行）、成本与耗时 |
| 子代理规格 `WorkerSpec` | 派生临时 worker 的规格单（F10） | 角色名、system_prompt、工具 allowlist、模型（含 provider）、超时、预算、最大轮次 |
| 子代理节点 `SubagentNode` | 控制台里的一棵树节点（F12） | subagent_id、父节点、角色、状态、耗时、模型、成本、最后输出摘要、是否可取消 |
| 执行记录 `ExecRecord` | 一条命令/脚本的审计条目（F11） | 发起方、命令原文、cwd、**风险等级（low/med/high/critical）**、独立判定理由与危险说明、退出码、耗时、输出摘要、拒绝原因、当时是否开启自动模式 |

## 9. 非功能需求

| 类别 | 要求 |
|---|---|
| 可观测 | 每次秘书决策必须可在调度面板回放：输入摘要、判定、模型、成本、结果 |
| 成本 | 成功路径零增量；失败路径单次决策成本见 §12.1；**预算是可选项**——配置时不可越，未配置时无上限（只记账不阻断） |
| 时延 | 单次决策 ≤ 8s（不含实际修复耗时）；等待期间 UI 必须有进度，不得白屏 |
| 幂等 | 同一账本状态下重复决策应产生同一致结论（可复现，便于排障） |
| 安全 | 命令执行必须经 `ExecutionGateway`：每次先由**独立 LLM 请求**判风险（输入隔离），`low` 放行、`med+` 弹框请用户授权并说明危险程度；规则表只「就高不就低」；判定失败 fail-safe 到 `high`；凭据读取与不可逆系统破坏被规则标记为 `critical` 并要求**两级确认**（可用设置项回退为直接拒绝）；环境变量剥离全部密钥 |
| 沙盒 | cwd 限定管线 workspace；墙钟默认 60s（可配至 600s）；输出截断；Python 必须子进程执行、默认禁网 |
| 审计 | 每次执行 / 每次派工 / 每次派生都**不可关闭**地入账本，可在控制台回放；记录当时是否处于自动模式 |
| 并发与配额 | 并发子代理上限由设置项 `max_concurrent_subagents` 控制（默认 6，用户可改）；**子代理开销不设独立上限**，全额计入管线预算 |
| 回滚 | 提供开关：关闭秘书后完全退回现状行为（含关闭模型路由与执行能力） |
| 上报完整性 | 阶段结束时「有降级但无登记」必须能被检出：账本条目数 ≠ 降级计数即为异常，记入管线诊断 |
| 数据合规 | 跨 provider 调用已开放，但需在部署文档/隐私条款披露「数据从哪家发往哪家」；私有化部署默认优先本地 provider |

## 10. 验收标准

| 编号 | 标准 | 验证方式 |
|---|---|---|
| A1 | 失败管线 ≥90% 产出诊断书且含「责任＋证据＋建议」 | 抽样 30 条历史失败管线回放 |
| A2 | 归因准确率 ≥80% | 人工核对 30 条 |
| A3 | 同策略连续重试 ≤1 次 | 构造「重做三次无效」用例 |
| A4 | 不可修复判定误标率 ≤10% | 人工核对 |
| A5 | 成功路径成本增量 = 0 | A/B 各 20 条同输入管线对比 token 账单 |
| A6 | 预算配置时不得越上限；未配置时不得出现「因预算被拒」 | 两种配置各测一次：配置上限/留空 |
| A7 | 质检评分路径未收到账本字段 | 契约测试（断言 `QualityInput` 不含账本字段） |
| A8 | 诊断书可被非技术用户读懂 | 5 人可用性测试，≥4 人通过 |
| A9 | 模型路由留痕完整 | 任取一条换模型记录，五个字段齐全 |
| A10 | 关闭开关后行为与现状等价 | 同输入产出 timeline 逐字节比对 |
| A11 | 6 个 Agent 的 FAIL 分支全部填充完整失败回报（七字段无缺） | 契约测试 ＋ 逐阶段构造失败用例回放 |
| A12 | 所有降级路径均产生降级声明，无静默吞错 | 静态扫描「`except: pass` / fallback 无记录」清单，逐项确认归零 |
| A13 | 下游「向上申报需求」能触发正确的上游重做 | 构造「material 申报缺 material_refs」用例，验证秘书走 S3 而非重做 material 自身三次 |
| A14 | 主代理可列出/查询/取消子代理，状态与实际一致 | 构造 3 并发子代理用例，控制台与后端状态逐项对齐 |
| A15 | 风险判定生效：`med` 及以上必弹框且弹框含「等级/会动到什么/后果」；`critical`（含硬底线）必须连过**两道**确认 | 构造 `rm -rf /`（critical，两道确认后放行）、删工程目录（high，一次确认）、读 `.env`（critical + hardFloor 标记）三类用例 |
| A15b | 硬底线回退开关有效 | `exec_hard_floor_never_authorizable=true` 时读 `.env` 直接拒且**不调用** LLM |
| A15c | 授权窗口过期不放行 | 待授权条目超 10 分钟后 approve 必须失败并留审计 |
| A16 | 每条命令/脚本都有审计条目（含被拒的、含风险等级与理由） | 抽 20 条 `ExecRecord` 核对字段齐全 |
| A17 | 临时 worker 生命周期正确，管线结束即回收 | 管线结束后 `list_subagents` 与 `AgentRegistry` 均为空 |
| A18 | 跨 provider 路由按派工单生效且记账到 `(stage, provider/model)`，记账不阻断调用 | 构造跨 provider 派工，核对 `llm_tracker` 与账本 |
| A19 | 子代理不能再派生子代理（星型，深度 1） | 构造子代理内调用 `spawn_subagent`，必须被拒并留痕 |
| A20 | 自动模式只减免 `med` 的弹框；`high` / `critical` 仍弹 | 开/关各测一次：开时 med 不弹、high 仍弹 |
| A21 | 独立判定必产出非空 `reasons` 与 `danger_explanation` | 抽 20 条判定记录，理由非空且非套话 |
| A22 | 带执行权限的临时 worker 未经「独立 LLM 判风险 → 人工审核」不得实例化 | 构造一个带 shell 的 worker：未审核时 spawn 必须失败；审核通过后才可创建 |
| A23 | 独立 LLM 的风险判定不看主代理辩解（输入隔离） | 断言判定请求体只含 WorkerSpec，不含主代理对话/理由字段 |
| A24 | 命令风险判定同样输入隔离（只含命令 + cwd + workspace 说明） | 断言 `risk_judge` 请求体字段白名单 |
| A25 | 就高不就低：LLM 判 `low` 但命中危险种子 → 强制升 `med` 弹框 | 构造「删除既有文件 / 装包 / 起服务 / 下载后执行」四类命令 |
| A26 | 判定失败（超时/非法 JSON）→ fail-safe 为 `high` 弹框，绝不静默放行 | 注入超时与坏 JSON 两种故障 |

## 11. 分期与依赖

| 期 | 范围 | 交付物 | 依赖 |
|---|---|---|---|
| **P0**（先做） | F9 失败回报契约（结构化失败/降级上报）＋ F1 账本（落库降级、警告、错误、模型、用量） | 账本能回答「这一步到底发生了什么、它自己说了什么」 | 无 |
| **P1** | F2 归因（确定性优先，仅冲突时用 LLM）＋ F5 诊断书 v1（模板化，无 LLM） | 失败可解释率从 0 到 ≥70% | P0 |
| **P2** | F3 策略 + F4 派工 + F8 模型路由（表内选） | 无效重试下降、成本可控 | P0、P1 |
| **P3** | F6 预算（**可选，未配置=无上限**）+ F7 升级接管 + 调度面板完整交互 | 可交付运营 | P2 |
| **P4**（可延后） | F8 二阶段（表内自由选 + 临时 worker 档位自主）＋ F10 动态子代理 | 秘书能临时派生新角色干活 | P2、P3 |
| **P5** | **F12 子代理观测 → F11 执行能力**（网关 + 五项能力） | 先看见子代理，再给 shell | P4；执行网关必须先于 shell 开放 |

> **顺序不可颠倒的理由**：没有 P0 的账本，秘书和今天的质检一样盲；先上秘书只会多一层 LLM 费用和一个新的不确定性来源。P1 落地后会发现一部分「需要判断」的场景自动消失（信息一全，静态归因就够准），剩下的才是秘书真正该干的活。
>
> **P5 为什么排最后**：F11 是整套需求里唯一「一旦做错就会真的损坏用户数据」的能力。它必须建立在两件事之上——账本已能审计（P0）、子代理可观测（F12）。先给 shell 后给观测，等于蒙着眼睛开车。

## 12. 待裁定问题（需拍板）

| 编号 | 问题 | 影响 |
|---|---|---|
| Q3 | 是否允许用户手动改派工单（人工接管深度） | F7 范围大小 |
| Q4 | 单次秘书决策成本上限、单管线最大换模型次数 | F3/F8 硬规则 |
| Q6 | 诊断书是否允许暴露内部阶段名（专业用户可能需要） | F5 文案与权限 |

> **已定（v1.4）**：
> ① **不区分免费/付费套餐**——所有用户共享同一套能力与规则。
> ② **允许跨 provider**；**记账保留但不阻断**（记账是观测，不是否决权）。
> ③ **命令风险由独立 LLM 请求判定**（输入隔离、独立模型/会话）：`low` 直接执行，`med`/`high`/`critical` 弹框请用户授权并写清危险程度；确定性规则表只「就高不就低」；「读凭据」与「不可逆系统破坏」被规则钉成 `critical` 并加一道再次确认（v1.5 起；设置项可回退为直接拒绝）。
> ④ **自动模式**：由用户在前端用按钮决定开关，默认关；开启后危险命令不再逐条弹窗，但审计不减免。
> ⑤ **并发子代理上限在设置中配置**；**子代理开销不设独立上限**，全额计入管线预算。
> ⑥ **预算与单价表在设置中配置；不填 = 无上限**（只记账、不阻断、不降级）。
> ⑦ **带执行权限的临时 worker 必须两级审核**：先由**独立 LLM**（独立会话/模型、输入不含主代理辩解）判定风险等级与理由，再由**人工审核**批准；`risk=high` 需显式二次确认；未过门不得实例化。

### 12.1 推荐默认值（待签字，签字后即为「已定」）

> 这些值的作用是让 B3/B4/B5 能开工。它们不是拍脑袋的大数，而是**从机制反推出来的最小值**：先定「怎么算」，再定「具体数字」。

| 编号 | 推荐值 | 依据 | 需要你确认的点 |
|---|---|---|---|
| **Q4-a 换模型次数** | 每管线 **≤2 次** | 超过 2 次说明不是模型能力问题，而是输入/资源问题，继续换是烧钱 | 是否放宽到 4 次（本期不分套餐） |
| **Q4-b 单次决策成本** | 秘书单次决策 ≤ **该阶段单次执行均值 × 0.15**；绝对上限按定价表填 | 决策本身不该比执行还贵 | 绝对上限数值 |
| **Q4-c 决策模型档位** | 归因/策略决策固定走 `cheap` 档（`use_flash`） | 这是分类与选择任务，不需要最强模型 | 是否允许「归因冲突」时升一档 |
| **Q5 跨 provider** | **已定：允许，记账不阻断** | 用户已拍板；记账只做观测，不做否决 | — |
| **Q1 预算/单价** | **已定：设置中配置；不填 = 无上限**（只记账、不阻断、不降级） | 用户已拍板；成本控制的闸从默认开启改为用户显式启用 | 无（可在设置页后续加引导文案） |
| **Q9 执行权限 worker** | **已定：两级门**——独立 LLM 判风险（输入隔离）→ 人工审核；`high` 需二次确认；未过门不得实例化 | 用户已拍板；独立性是为了防止主代理把自己说服 | 独立判定用哪个模型/是否允许换模型 |

## 13. 风险与缓解

| 风险 | 后果 | 缓解 |
|---|---|---|
| 归因错误被放大 | 秘书自信地重做错阶段，比现状更贵更慢 | 置信度低时降级为「静态归因 + 上报」，不硬派工；A2 门限卡住上线 |
| 「换模型」变成「花钱试错」 | 成本飙涨 | 白名单 + 预算硬熔断 + 冷启动只允许表内选 |
| 用户信任 | 自动重试静默发生，用户不知道钱花在哪 | 调度面板 + 成本条 + 一键动作二次确认 |
| 引入 LLM 决策后不可复现 | 排障困难 | 决策幂等（同账本同结论）＋ 关开关可退现状 |
| 账本信息回流质检 | 自愈退化为自动签批 | A7 契约测试硬卡 |
| **shell/python 被误用或逃逸** | 删错文件、泄露密钥、损坏用户工程 | 独立 LLM 风险判定（输入隔离）+ 规则表「就高不就低」+ 判定失败 fail-safe 到 high + 凭据/系统破坏硬底线 + cwd 限定 + 环境变量剥离 + 全量审计；自动模式由用户显式开关并全程留痕；明确「审计边界 ≠ 安全边界」，不可信代码必须上容器 |
| **临时 worker 自我扩权** | 派生一个「拥有全部工具、无限预算」的 worker，把约束绕过去 | worker 工具集只能是主代理子集；并发与预算硬顶；提示词落库可追责（A17/A19） |
| **子代理失控/打爆成本** | 一次失败派生 20 个子代理同时跑 | 并发上限 + 子代理总预算占比 + 秘书每轮派生次数上限 |
| **跨 provider 数据出境** | 内容被发到不允许的地区 | 白名单 + 每次跨 provider 记账「从哪家到哪家」+ 私有化部署默认本地优先 |
| **默认无预算上限 → 成本失控** | 一次失控的排查循环把钱烧光且不叫停 | 成本条常驻显示；按日/按项目汇总与「涨速异常」告警（只告警不阻断）；设置页给出「建议开启预算」引导 |
| **审核门被绕过或形式化** | 人工审核一键通过，等于没有审核 | `risk=high` 强制二次确认；两级结论都入账；A22/A23 契约测试卡住 |
